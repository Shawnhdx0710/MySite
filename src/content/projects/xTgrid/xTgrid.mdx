To understand Expected Threat (xT) and an xT grid, please read [Karun Singh's original 2018 blog post](https://karun.in/blog/expected-threat.html). Since xT's introduction, the metric has been reimplemented across an entire ecosystem of open-source tools.

**[`socceraction`](https://github.com/ML-KULeuven/socceraction).** Reserachers at KU Leuven built a full pipeline. Their [notebook](https://github.com/ML-KULeuven/socceraction/blob/master/public-notebooks/1-load-and-convert-statsbomb-data.ipynb) walked through every step. However, it loaded a pre trained model and assumed the legacy `statsbombpy` event format, which, as we'll see, is the central problem this project had to solve.

**[`mplsoccer`](https://mplsoccer.readthedocs.io/en/latest/gallery/tutorials/plot_xt.html).** This is a Python xT tutorial, using a 16×12 grid.

**[`penaltyblog`](https://penaltyblog.readthedocs.io/en/master/xt/index.html).** This module solved the xT equation directly with linear algebra rather than value iteration. A pre-trained model trained with ~14M events from Europe's Big 5 leagues was mentioned. [Soccermatics course notebook](https://soccermatics.readthedocs.io/en/latest/gallery/lesson4/plot_ExpectedThreat.html), just like the mplsoccer tutorial, can help readers to understand the underlying logic of xT with a simple demonstration. 

**[McKay Johns](https://www.mckayjohns.com/).** His [YouTube channel](https://youtube.com/c/McKayJohns) and [GitHub repos](https://github.com/mckayjohns) (notably [`complete-football-analytics`](https://github.com/mckayjohns/complete-football-analytics)) cover the full Python analytics stack. The repo contains a downloadable xT grid in CSV format, yet the training datasets are unspecified.

**[The Athletic](https://www.nytimes.com/athletic/2751525/2021/08/06/introducing-expected-threat-or-xt-the-new-metric-on-the-block/).** This is one of the earliest mainstream media introductions to xT. It published an xT grid as part of the explainer.

**[`databallpy`](https://databallpy.readthedocs.io/en/latest/features/xt_models.html).** This is a Python package that contains a 32×24 xT grid, trained with event data of over 600 games that is not publicly available. 

### What This Project Does?

All of these tools either (a) ship a pre-trained grid and use it to make further analysis without showing the training pipeline, (b) train a grid only on a small subset of matches for demonstration purposes, or (c) rely on library versions that no longer work together. None of them provide an *end-to-end, resumable, memory-efficient pipeline* that can train a high-resolution 32×24 grid on a large number of event datasets from a consumer laptop.

So, I built a pipeline that:

- Fetches the event data from all 3,927 publicly available matches in the [StatsBomb Open Data repository](https://github.com/statsbomb/open-data)
- Converts raw event data to [SPADL](https://socceraction.readthedocs.io/en/latest/documentation/spadl/spadl.html) using a custom converter that bridges the `statsbombpy`/`socceraction` version mismatch
- Caches every match as compressed Parquet 
- Trains an xT grid at 32×24 resolution
- Runs entirely on an M1 MacBook Air with 8 GB of RAM

## Environment

There are several important questions need to be considered:

**Can an 8 GB M1 handle this?** The StatsBomb Open Data repository contains roughly 3,900 matches. Each match is a JSON file containing 2,000–4,000 events. Loading everything into memory as raw JSON would consume gigabytes. But SPADL conversion helps discard irrelevant events and keeps only ball actions. Each match then compresses to roughly 1,500–2,000 rows. At ~100 bytes per row with only the columns the xT model needs, the full dataset fits in about 600 MB of RAM during training. This totally workable.

**What library versions?** This is where things got complicated.

**Will the disk survive?** 3,900 JSON files at ~1 MB each equal ~4 GB of raw download traffic. But stored as zstd-compressed Parquet, the entire cache shrinks to only 210 MB. 

### Version

The pipeline relies on two libraries: [`socceraction`](https://github.com/ML-KULeuven/socceraction) (for SPADL conversion and xT) and [`statsbombpy`](https://github.com/statsbomb/statsbombpy) (for fetching StatsBomb event datasets). They should've work well together. However, older versions of `statsbombpy` (v0.x) returned events with a nested `extra` column:

```python
# Legacy format: nested dicts
events["extra"] = {
    "pass": {
        "end_location": [75.0, 35.0],
        "outcome": {"name": "Complete"},
        "body_part": {"name": "Right Foot"},
    }
}
```

Every modern version (v1.0+) flattens these into prefixed columns:

```python
# Modern format: flattened columns
events["pass_end_location"] = [75.0, 35.0]
events["pass_outcome"] = "Complete"
events["pass_body_part"] = "Right Foot"
```

`socceraction` v1.5.3 expects the legacy format. Its `convert_to_actions()` function accesses `events.type_name`, `events.extra`, and `events["extra"]["pass"]["outcome"]["name"]`. None of these exist in modern `statsbombpy`. The v0.1 release that *did* use the legacy format fails to install on Python 3.12 because its caching layer (`cashier`) depends on `dummy_thread`, a module deleted in Python 3.7.

**Attempted fixes that didn't work:**

| Attempt | Result |
|---|---|
| Downgrade `statsbombpy` to v0.1 | `ModuleNotFoundError: No module named 'dummy_thread'` |
| Downgrade `statsbombpy` to v1.3.0 | Still flattened format — no `extra` column |
| Downgrade `statsbombpy` to v1.7.0 | Same |
| Reconstruct legacy `extra` dict from flattened columns | Too complex as each event type has different nested structures |

My solution is to **write a custom SPADL converter** myself. Here's the core mapping logic for just the pass-type differentiation:

```python
# A "Pass" in StatsBomb could be 8 different SPADL action types:
mask_pass = df["type"] == "Pass"

# Throw-in
df.loc[mask_pass & (df["pass_type"] == "Throw-in"), "type_id"] = TYPE2ID["throw_in"]

# Goal kick
df.loc[mask_pass & (df["pass_type"] == "Goal Kick"), "type_id"] = TYPE2ID["goalkick"]

# Free kick → crossed or short?
is_fk = df["pass_type"] == "Free Kick"
df.loc[mask_pass & is_fk & df["pass_cross"], "type_id"] = TYPE2ID["freekick_crossed"]
df.loc[mask_pass & is_fk & ~df["pass_cross"], "type_id"] = TYPE2ID["freekick_short"]

# Corner → crossed or short?
is_corner = df["pass_type"] == "Corner"
df.loc[mask_pass & is_corner & df["pass_cross"], "type_id"] = TYPE2ID["corner_crossed"]
df.loc[mask_pass & is_corner & ~df["pass_cross"], "type_id"] = TYPE2ID["corner_short"]

# Open-play cross (not a set piece, but pass_cross=True)
df.loc[mask_pass & df["pass_cross"] & ~df["pass_type"].isin(
    ["Throw-in", "Goal Kick", "Free Kick", "Corner"]
), "type_id"] = TYPE2ID["cross"]
```

This pattern repeats for every event type: shots, carries, dribbles, goalkeeper actions, duels, interceptions, clearances. The converter uses boolean masks (`df["type"] == "Shot"`) rather than row-by-row iteration, so one match can converts quickly.

A second dependency conflict surfaced during import: `socceraction` depends on `pandera` v0.17.x, which calls `from multimethod import overload`. But `multimethod` v2.x removed that function. The fix (`pip install 'multimethod<2.0.0'`) is pinned in `requirements-xt.txt`.

## Caching

The pipeline processes 3,927 matches. Each match requires an HTTP round-trip to GitHub's raw content servers. At ~2 seconds per match, that's over 2 hours of time. If the script crashes at some point, re-running wouldn't be fun.

My solution is a file-system cache with one Parquet file per match:

```
sb_cache/spadl_parquet/
├── 8650.parquet   ← Brazil v Belgium, 2018 QF
├── 8651.parquet   ← France v Argentina, 2018 R16
├── 8652.parquet   ← Uruguay v Portugal, 2018 R16
├── ...
└── 3910944.parquet
```

The logic is simple:

```python
def process_match(match_id):
    if cache_path(match_id).exists():   # ← cache hit: skip everything
        return "cached"

    events = download(match_id)          # ← only if not cached
    actions = convert_to_spadl(events)   # ← CPU work done once
    actions.to_parquet(cache_path)       # ← persist forever
    return "done"
```

This makes the pipeline **idempotent**. Re-running it always produces the same result, and already-processed matches are skipped instantly. 

### Why Parquet?

1. A typical match is ~1 MB. After SPADL conversion and zstd Parquet compression, it's ~50 KB. The full cache is around 210 MB for 3,927 matches, which is a 20× reduction from the raw JSON.

2. The xT model only needs 6 of the 13 columns in each file (`start_x`, `start_y`, `end_x`, `end_y`, `type_id`, `result_id`). PyArrow's `pq.read_table()` loads only those columns, skipping the other 7 entirely. Loading 13.7 million rows across 3,927 files takes **1.7 seconds**.

3. CSV and JSON require parsing strings into floats and ints. Parquet stores native binary types.

## Training

With all 3,927 matches cached, training is almost anticlimactic:

```python
from socceraction.xthreat import ExpectedThreat

model = ExpectedThreat(l=32, w=24, eps=1e-5)
model.fit(actions)   # 13.7M actions, 41 iterations, 14.6 seconds
```

The grid converges through value iteration. Each cell starts at zero. In each iteration, the algorithm computes:

```
xT(cell) = P(shoot | cell) × P(goal | shoot, cell)
         + P(move | cell) × Σ [ P(land in cell' | move) × xT(cell') ]
```

The full pipeline is available at [github.com/shawnhdx0710/shawnhdx0710.github.io](https://github.com/shawnhdx0710/shawnhdx0710.github.io) in the `scripts/` directory. The trained grid is in `output/xt_grid_32x24.npy`.
