To understand Expected Threat (xT) and an xT grid, please read [Karun Singh's original 2018 blog post](https://karun.in/blog/expected-threat.html). Since xT's introduction, the metric has been reimplemented across an entire ecosystem of open-source tools.

**[`socceraction`](https://github.com/ML-KULeuven/socceraction) (KU Leuven).** The most academically rigorous implementation.Reserachers at KU Leuven built a full pipeline: load data from StatsBomb/Opta/Wyscout, convert to the SPADL unified action format, train an xT model via `ExpectedThreat(l=16, w=12)`, rate individual actions. Their [notebook](https://github.com/ML-KULeuven/socceraction/blob/master/public-notebooks/1-load-and-convert-statsbomb-data.ipynb) walks through every step. However, it assumes the legacy `statsbombpy` event format, which, as we'll see, is the central problem this project had to solve.

**[`mplsoccer`](https://mplsoccer.readthedocs.io/en/latest/gallery/tutorials/plot_xt.html) (Andrew Rowlinson).** A comprehensive Python xT tutorial using FA Women's Super League data. Uses a 16×12 grid following Karun Singh's original setup. Great resource to understand *how* xT works .

**[`penaltyblog`](https://penaltyblog.readthedocs.io/en/master/xt/index.html) (David Sumpter / Friends of Tracking).** Solves the xT equation directly with linear algebra rather than value iteration. Ships with a pre-trained model fit on ~14M events from Europe's Big 5 leagues. Also provides the [Soccermatics course notebook](https://soccermatics.readthedocs.io/en/latest/gallery/lesson4/plot_ExpectedThreat.html) with a full Wyscout implementation.

**[McKay Johns](https://www.mckayjohns.com/).** A sports analytics educator whose [YouTube channel](https://youtube.com/c/McKayJohns) and [GitHub repos](https://github.com/mckayjohns) (notably [`complete-football-analytics`](https://github.com/mckayjohns/complete-football-analytics)) cover the full Python analytics stack. The repo contains a downloadable CSV xT grid that is ready to use without any training.

**[The Athletic](https://www.nytimes.com/athletic/2751525/2021/08/06/introducing-expected-threat-or-xt-the-new-metric-on-the-block/) (Tom Worville, August 2021).** One of the earliest mainstream media introductions to Expected Threat. Published an xT grid as part of the explainer, giving readers their first look at what a trained threat surface actually looks like.

**[`databallpy`](https://databallpy.readthedocs.io/en/latest/features/xt_models.html).** A Python package that contains a 32×24 xT grid, trained with event data of over 600 games that is not publicly available. 

### What This Project Does?

All of these tools either (a) ship a pre-trained grid and use it to make further analysis without showing the training pipeline, (b) train a grid only on a small subset of matches for demonstration purposes, or (c) rely on library versions that no longer work together. None of them provide an *end-to-end, resumable, memory-efficient pipeline* that can train a high-resolution 32×24 grid on a large number of event datasets from a consumer laptop.

So, I built a pipeline that:

- Fetches the event data from all 3,927 publicly available matches in the [StatsBomb Open Data repository](https://github.com/statsbomb/open-data)
- Converts raw event data to SPADL using a custom converter that bridges the `statsbombpy`/`socceraction` version mismatch
- Caches every match as compressed Parquet 
- Trains an xT grid at 32×24 resolution
- Runs entirely on an M1 MacBook Air with 8 GB of RAM

## Environment

There are several important questions need to be considered:

**Can an 8 GB M1 handle this?** The StatsBomb Open Data repository contains roughly 3,900 matches. Each match is a JSON blob of 2,000–4,000 events. Loading everything into memory as raw JSON would consume gigabytes. But after SPADL conversion — which discards irrelevant events (starting XIs, tactical shifts, camera changes) and keeps only ball actions — each match compresses to roughly 1,500–2,000 rows. At ~100 bytes per row with only the columns the xT model needs, the full dataset fits in about 600 MB of RAM during training. This is tight but workable.

**What library versions?** This is where things got complicated.

**Will the disk survive?** 3,900 JSON files at ~1 MB each = ~4 GB of raw download traffic. But stored as zstd-compressed Parquet, the entire cache shrinks to only 210 MB. 

### Version

The pipeline, like many projects in soccer analytics, relies on two libraries: [`socceraction`](https://github.com/ML-KULeuven/socceraction) (for SPADL conversion, xT, and VAEP models) and [`statsbombpy`](https://github.com/statsbomb/statsbombpy) (for fetching StatsBomb event data). In theory, they can work together. However, The problem is: older versions of `statsbombpy` (v0.x) returned events with a nested `extra` column:

```python
# Legacy format: nested dicts
events["extra"] = {
    "pass": {
        "end_location": [75.0, 35.0],
        "outcome": {"name": "Complete"},
        "body_part": {"name": "Right Foot"},
    }
}
```

Every modern version (v1.0+) flattens these into prefixed columns:

```python
# Modern format: flattened columns
events["pass_end_location"] = [75.0, 35.0]
events["pass_outcome"] = "Complete"
events["pass_body_part"] = "Right Foot"
```

`socceraction` v1.5.3 — the latest stable release — expects the legacy format. Its `convert_to_actions()` function accesses `events.type_name`, `events.extra`, and `events["extra"]["pass"]["outcome"]["name"]`. None of these exist in modern `statsbombpy`. The v0.1 release that *did* use the legacy format fails to install on Python 3.12 because its caching layer (`cashier`) depends on `dummy_thread`, a module deleted in Python 3.7.

**Attempted fixes that didn't work:**

| Attempt | Result |
|---|---|
| Downgrade `statsbombpy` to v0.1 | `ModuleNotFoundError: No module named 'dummy_thread'` |
| Downgrade `statsbombpy` to v1.3.0 | Still flattened format — no `extra` column |
| Downgrade `statsbombpy` to v1.7.0 | Same |
| Reconstruct legacy `extra` dict from flattened columns | Exploded in complexity — 15+ event types, each with different nested structures |

I found that one solution is to **write a custom SPADL converter** myself. Here's the core mapping logic for just the pass-type differentiation:

```python
# A "Pass" in StatsBomb could be 8 different SPADL action types:
mask_pass = df["type"] == "Pass"

# Throw-in
df.loc[mask_pass & (df["pass_type"] == "Throw-in"), "type_id"] = TYPE2ID["throw_in"]

# Goal kick
df.loc[mask_pass & (df["pass_type"] == "Goal Kick"), "type_id"] = TYPE2ID["goalkick"]

# Free kick → crossed or short?
is_fk = df["pass_type"] == "Free Kick"
df.loc[mask_pass & is_fk & df["pass_cross"], "type_id"] = TYPE2ID["freekick_crossed"]
df.loc[mask_pass & is_fk & ~df["pass_cross"], "type_id"] = TYPE2ID["freekick_short"]

# Corner → crossed or short?
is_corner = df["pass_type"] == "Corner"
df.loc[mask_pass & is_corner & df["pass_cross"], "type_id"] = TYPE2ID["corner_crossed"]
df.loc[mask_pass & is_corner & ~df["pass_cross"], "type_id"] = TYPE2ID["corner_short"]

# Open-play cross (not a set piece, but pass_cross=True)
df.loc[mask_pass & df["pass_cross"] & ~df["pass_type"].isin(
    ["Throw-in", "Goal Kick", "Free Kick", "Corner"]
), "type_id"] = TYPE2ID["cross"]
```

This pattern repeats for every event type: shots, carries, dribbles, goalkeeper actions, duels, interceptions, clearances. The converter uses boolean masks (`df["type"] == "Shot"`) rather than row-by-row iteration, so one match can converts quickly.

A second dependency conflict surfaced during import: `socceraction` depends on `pandera` v0.17.x, which calls `from multimethod import overload`. But `multimethod` v2.x removed that function. The fix (`pip install 'multimethod<2.0.0'`) is pinned in `requirements-xt.txt`.

## Caching

The pipeline processes 3,927 matches. Each match requires an HTTP round-trip to GitHub's raw content servers. At ~2 seconds per match, that's over 2 hours of time. If the script crashes at some point, re-running wouldn't be fun.

My solution is a file-system cache with one Parquet file per match:

```
sb_cache/spadl_parquet/
├── 8650.parquet   ← Brazil v Belgium, 2018 QF
├── 8651.parquet   ← France v Argentina, 2018 R16
├── 8652.parquet   ← Uruguay v Portugal, 2018 R16
├── ...
└── 3910944.parquet
```

The logic is simple:

```python
def process_match(match_id):
    if cache_path(match_id).exists():   # ← cache hit: skip everything
        return "cached"

    events = download(match_id)          # ← only if not cached
    actions = convert_to_spadl(events)   # ← CPU work done once
    actions.to_parquet(cache_path)       # ← persist forever
    return "done"
```

This makes the pipeline **idempotent** — re-running it always produces the same result, and already-processed matches are skipped instantly. When the full run finished at 3,927 matches, I could re-run the entire script and it would report `✓0 ↪3927 ✗0` in under a second.

### Why Parquet?

1. **Compression.** A typical match is ~3,500 JSON events (~1 MB raw). After SPADL conversion and zstd Parquet compression, it's ~50 KB. The full cache is 210 MB for 3,927 matches, which is a 20× reduction from the raw JSON.

2. **Columnar reads.** The xT model only needs 6 of the 13 columns in each file (`start_x`, `start_y`, `end_x`, `end_y`, `type_id`, `result_id`). PyArrow's `pq.read_table()` loads only those columns, skipping the other 7 entirely. Loading 13.7 million rows across 3,927 files takes **1.7 seconds**.

3. **No deserialization overhead.** CSV and JSON require parsing strings into floats and ints. Parquet stores native binary types — the data lands in memory ready to use.

Parquet isn't just "a better CSV." It's a fundamentally different storage model: columnar, binary, compressed, and metadata-rich. 

## Training

With all 3,927 matches cached, training is almost anticlimactic:

```python
from socceraction.xthreat import ExpectedThreat

model = ExpectedThreat(l=32, w=24, eps=1e-5)
model.fit(actions)   # 13.7M actions, 41 iterations, 14.6 seconds
```

The grid converges through value iteration. Each cell starts at zero. In each iteration, the algorithm computes:

```
xT(cell) = P(shoot | cell) × P(goal | shoot, cell)
         + P(move | cell) × Σ [ P(land in cell' | move) × xT(cell') ]
```

## What This Pipeline Gets Right In My Opinion

**Idempotency.** The cache script can be killed at any point and restarted without penalty. Each match is an independent file. No global state, no partial downloads to clean up.

**Separation of concerns.** Three scripts, three responsibilities. `01_cache_spadl.py` fetches and converts. `02_train_xt.py` loads and trains. `03_visualize_xt.py` plots. You can re-train a hundred times on different parameter settings without re-downloading anything. You can tweak the visualization colormap without touching the data pipeline.

**Vectorized pandas, not for-loops.** The SPADL converter processes all 3,500 events in a match simultaneously through boolean masks. On the M1, this is the difference between ~3 ms and ~300 ms per match — multiplied by 3,927 matches, that's the difference between 12 seconds and 20 minutes of CPU time.

**Graceful degradation.** Network errors are caught per-match. One bad download produces a log entry, not a crashed pipeline. In the full run, exactly one match failed (a transient SSL error on GitHub's CDN). The other 3,927 succeeded.
